### The mechanism

Nothing in the chrome defers the footer. It is a server component rendered in the initial HTML; `ClientIslands` (`ssr: false`) mounts only `LanguageHint`/`ConsentBanner` *after* the chrome; no `hidden`-until-JS class, no `Suspense` boundary, no CLS-avoidance code touches `<footer>`; `display: swap` paints text in the fallback font immediately (next/font ships size-adjusted fallback metrics). The footer paragraph (`home.188`, 100+ characters of `text-white/65` on navy) is simply the **largest text node inside the 412×823 emulated viewport on a page whose `<main>` holds a one-word `<h1>` and one link** — an artefact of the placeholder homepage, not of the chrome.

Lighthouse's Lantern model estimates a text LCP as `0.5 × optimistic + 0.5 × pessimistic`, where the optimistic graph is render-blocking resources only (≈ FCP, 905 ms) and the **pessimistic graph is every network request that *started* before the observed LCP** — and in an unthrottled trace with LCP at 49 ms that is the whole initial waterfall: 11 module scripts (177,782 B), the two preloaded fonts (68,212 B), the CSS, the logo preloads and the document (≈ 299 KB total). Simulated over Lantern's 1.6 Mbps / 150 ms RTT link, that graph completes at ≈ 4.8 s, so LCP ≈ (0.9 + 4.8) / 2 ≈ 2.86 s. TTI equals LCP because Lantern's TTI is `max(LCP, last long task)` and there are no long tasks (TBT 0) — the "LCP ≈ TTI" that looked like hydration blocking paint is a modelling identity. The experiments confirm the attribution: removing all script takes 1,053 ms off the simulated LCP (≈ 5.9 ms per KB of first-load script), removing fonts as well takes 1,499 ms off; what remains (1,357 vs FCP 903) is the document, CSS and image preloads in the same graph. On the preview the same model adds the real edge TTFB (Lantern uses the observed server latency), which is why the preview read FCP 1.0 s / LCP 3.0 s; its Speed Index 3.9 s (locally 0.9 s) is the one **real** signal in the finding: over a real network the two font files land late enough that the Archivo swap changes pixels after first paint, and Lantern scales that observed visual-completeness gap up. Performance 0.93 vs 0.96 follows arithmetically from LCP 3.0 (≈ 0.77 on the LH 12 curve, weight 25 %) and SI 3.9 (≈ 0.66, weight 10 %) with FCP/TBT/CLS perfect.

**Root cause, in one sentence:** W141 is Lantern's pessimistic-graph charge on a text LCP element (every byte of the initial waterfall counts toward the paint of a paragraph that needs none of them) on a placeholder page whose largest in-viewport text happens to be in the footer; observed and DevTools-throttled traces show no deferred paint at all.

### Fixes and expected impact

1. **The gate's LCP assertion must change how it measures, not what it wants (⚠️ ruling 1).** At the framework floor (react-dom + App Router runtime 121 KB, next-intl 17 KB, chrome 20 KB, fonts 68 KB) no page can pass `LCP ≤ 2,500 ms` under Lantern: even with *every* first-load chunk removed the placeholder reads 1,803 ms, and real pages add a hero image (Load Delay/Load Time phases) and more DOM. Under real DevTools throttling the same page measures LCP 1,552 ms and performance 0.99. Recommendation: `lighthouserc.json`/`.preview.json` → `collect.settings.throttlingMethod: "devtools"`, `numberOfRuns: 3`, `assert.aggregationMethod: "median"` (keep all seven assertions as they are; `lighthouserc.local.json` can then stop waiving LCP — the R50 waiver existed only for Lantern). Cost: each run takes the real throttled time (~15 s) and needs three runs for stability; 14 pages × 2 locales × 3 runs ≈ 20 min per gate run. Alternative: keep simulation but set `largest-contentful-paint` `maxNumericValue` to a floor-aware lab value (≈ 3,200 ms) and `performance` `minScore` 0.90, with the PRD §6 2.5 s target enforced in the field (Vercel Speed Insights / CrUX at Gate A and the 12-week watch). Not acceptable: leaving the rc as it is — the preview gate stays red on every WP2b page by construction.
2. **Shrink the graph anyway (§2 diet).** Every KB of first-load script is ≈ 6 ms of simulated LCP and real bytes on a real phone: the chrome diet below (≈ 8–10 KB) is worth ≈ 50–60 ms; keeping fonts at two files (never a third weight/subset) matters more than any single chunk (68 KB ≈ 450 ms in the model).
3. **Keep `display: 'swap'`** (brand; CLS 0 thanks to next/font's fallback metrics). `optional` would remove the preview's SI penalty but shows system-font headings to every slow first visit — a pixel-fidelity call for the owner (⚠️ ruling 5), to be taken only if SI stays > 3.4 s after the diet.
4. **Nothing to fix in the footer or the chrome for W141.** The element will stop being the LCP candidate the moment T1 renders a hero.

### WP2b consequence — what every page must do to stay under the production rc

Read the rc: `largest-contentful-paint ≤ 2,500` (error), `categories:performance ≥ 0.95`, `accessibility/best-practices/seo = 1.0`, `resource-summary:script:size ≤ 204,800`, `cumulative-layout-shift ≤ 0.1`, `total-blocking-time ≤ 200` (warn). After ruling 1, the page rules are: (a) name the LCP element deliberately — the hero image through `ImageSlot lcp` (`preload`, explicit `width`/`height`, `sizes` for fluid slots) or the `<h1>` on a gradient hero, never something below it; (b) no `ssr: false` island and no `LazyIsland` fallback swap *inside the first viewport* (a fallback that differs from the island's DOM is a CLS and an LCP re-candidate); (c) first-load script stays flat — islands load through `LazyIsland`/interaction, forms below the fold too; (d) two font files, no extra weights; (e) document weight stays small — the 74 KB `SourceMap` SVG appears **twice** (HTML + RSC flight) when rendered by a server component: T1/T2 should ship it as a static `<img src="/brand/source-map-<locale>.svg">` (with its `<style>` inside the file) or render it below the fold only; (f) no third-party script before interaction except GTM, which must stay dark on the gated face (⚠️ ruling 2).
