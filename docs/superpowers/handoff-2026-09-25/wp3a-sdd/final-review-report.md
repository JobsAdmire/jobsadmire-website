## Issues

### Critical

### Important

1. **Plan-level: the D25 synthetic lead through the real form path cannot pass Turnstile in production — the PRD states it as the contract.** `website-captcha.service.ts:63-65` degrades only when no secret is stored; with the real secret, a headless monitor has no widget token, so `!token` → `failed` → 403 before any row (`website-forms.service.ts:234-235`). The gate's §H works only because it temporarily swaps in Cloudflare's always-pass secret. PRD §5.12 "Test class = the door, not the side effects" (docs/PRD.md:4192) promises a 30-minute synthetic lead that "measures the whole path up to the handler" — that heartbeat will be a permanent 403 once the real secret is stored. *Not a blocker for the two door-off pushes*, but it must be decided before WP2/WP5 wire monitoring. Fix (recommended): the `test` class skips `verify()` when `captchaToken` is absent (row `captchaPassed: null`, `captchaDegraded: false`, no alarm) — the test token is itself a server-held secret, so this widens nothing; alternatively redefine D25's heartbeat as `ping` and say so in §5.12.
2. **PRD §7.10's hardening table is wrong on two facts the sanction argument rests on** (docs/PRD.md:4681, 4684). (a) "fraud evidence is multipart … **≤ 3 files**" — the route accepts ONE file per call (`website-public-uploads.controller.ts:49` `files: 1, fields: 0`); Task 12's fix corrected §5.12 but not §7.10. (b) "an unauthenticated call is a 401 **before any body is parsed**" — true for multipart (multer is an interceptor, after guards) but false for the JSON forms route: `json({ limit: '1mb' })` is Express middleware (`main.ts:35`) and runs before every guard, so a tokenless 1 MB POST is parsed, then 401'd. Fix: one-line edits — "one file per call, ≤ 8 MB (3 per report)" and "…a 401 before any *handler* runs; JSON bodies are bounded by the global 1 MB parser, multipart is not read until the guards pass". The docs guard should pin the corrected `files: 1` sentence in §7.10 the way it pins §5.12.
3. **The WP3a rollback path is not written down.** DEPLOYMENT.md has the flip and the shut-the-door recipes (`:199-231`) and the generic `--rollback` section (`:341-348`), but nowhere says, for these two pushes: *rollback = `git revert <code sha>` on `main` (the poller redeploys in ~2 min); the migration is additive and stays; the seed's `since: 3` grant rows, the two `module_notification_settings` rows and the ten `website_forms` rows stay and are harmless (the resolver ignores keys no module registers — `packages/permissions/src/effective.ts` has no unknown-key throw); a re-apply later will NOT re-create those rows because `defaultsVersion` is already 3.* Add that paragraph under "Flipping `WEBSITE_MODULE_ENABLED` on the VPS" (or the gate record §E) before the code push — it is the one thing the on-call person needs at 03:00.

### Minor

4. **PII retention gap: rows that never reach HANDLED are never purged.** `purgeAfter` is set only on SPAM (`website-forms.service.ts:228`) and on handler success (`:413`); FAILED rows, dry-run FAILED rows, and RECEIVED rows whose outcome update failed keep name/phone/e-mail forever. Likewise `website_subscribers` PENDING rows with expired tokens are never removed (`website-purge.cron.ts:51-53` deliberately skips subscribers). Suggest: `purgeAfter = createdAt + 90 d` at row creation for every status (HANDLED merely resets it), and a PENDING-expired sweep (30 d) in the same cron. Spec letter says "post-HANDLED", so record as an owner decision.
5. **Stuck RECEIVED rows are silent.** If `inquiries.create` succeeds and the outcome `update` fails (`website-forms.service.ts:417-420`), the DB row stays `RECEIVED` with no entity: correctly *not* re-runnable (no double-file), but invisible to `needsAttention` (`website-forms-inbox.logic.ts:130-132` = FAILED ∨ captchaDegraded). Suggest `needsAttention` also matches `RECEIVED` older than ~10 min.
6. **Redis outage latency is bounded but long.** `RedisService` uses ioredis defaults (`redis.service.ts:13-19`: offline queue on, `maxRetriesPerRequest` 20 → a command issued mid-outage rejects only after ≈10 s of reconnect back-off). One POST does `isTripped` + `recordVerified` (+ the alarm SETNX) → 20–30 s before the fail-open path answers; the website's server action will time out first, the visitor sees the fallback panel, and the retry replays the row (correct, but ugly). Repo-wide posture, not new; a `Promise.race` timeout of ~1 s in `WebsiteAbuseService`/`WebsiteNotifyService` would keep the door under the website's budget.
7. **Careers DTO-validation failures alarm as infrastructure.** `careers-apply.handler.ts:84-91` returns `{ ok: false }` without `visitorError: true` when a *required* `PublicApplyDto` rule fails, so `handlerFailed` fires and the second human is mailed for what is the visitor's input. Add `visitorError: true` there (the catalog already mirrors the DTO caps, so this is rare).
8. **`@Throttle` tracker will be wrong the day `RATE_LIMITING_ENABLED` flips.** `RateLimitGuard.getTracker` keys on `X-Forwarded-For` (`rate-limit.guard.ts:56-63`) = the website's egress for every visitor, so the door's `10/min` (uploads) and `30/min` (newsletter) would be company-wide buckets. When enabling, the website routes need a tracker on `X-Website-Visitor-Ip`. (The inert state itself is already known.)
9. **Honeypot SPAM rows count as "real" for drought and `ping.lastSubmissionAt`** (`website-alarms.cron.ts:90-96`, `website-ping.service.ts:47-51` filter only `isTest: false`). A bot-only week masks a drought. Add `status: { not: SPAM }` to both queries.
10. **Heartbeat dedupe trap for WP5**: an identical synthetic payload posted twice in one hour replays the first row (`hourBucket`), so the dry-run handler runs at most once per hour per payload. The monitor must vary a field (timestamp) — say so in §5.12's heartbeat sentence.
11. **Evidence "View" bypasses the backend's CSP.** The inbox blob-fetches the stream and navigates a tab to a `blob:` URL (`inbox/page.tsx:118-146`); blob URLs carry no response headers, so `nosniff` + `default-src 'none'` set in `website-fraud-evidence.service.ts:112-116` are discarded and a PDF renders in the Operations origin. Mitigated by the 4-type magic-byte sniff at upload; the `hrm/persons/[id]` precedent does the same. A sandboxed `<iframe>` viewer later would restore the headers' intent.
12. **Templates pinned on disk only for autoresponders.** `website-autoresponder.service.spec.ts:46-47` asserts the 16 files; the newsletter pair ×2 and `website-forms-unavailable` ×2 exist but are pinned by name only (`event-registry-website.spec.ts:81`). A rename would surface as a failed mail job, not a red test.
13. **Abuse threshold sanity**: `WEBSITE_ABUSE_TRIP_THRESHOLD = 25` captcha-verified leads/hour/form (`website-alarms.logic.ts:15`) 429s *real* visitors for an hour after a successful campaign burst. By design (D11), but the owner should confirm the number before the flip.
14. **Docs nits**: PRD §5.12 anchors the intake order at `website-forms.service.ts:187-200` (that range is trip check → whitelist; honeypot/captcha/row are 226–241); gate record B2's checkbox reads "`exit=0`" while the recorded output and X4 say exit 2 (docs/superpowers/plans/2026-09-19-wp3a-gate-record.md:90); DEPLOYMENT `:117` says "every website cron returns at the top of its tick" — true, though the purge cron logs a line each night while off (`website-purge.cron.ts:81`), harmless.
15. **Agreement with parked items**: the two distinguishable 401 bodies (`website-api.guard.ts:48,55`) do leak "not configured" to an unauthenticated caller; still acceptable (call-center precedent, and the door is 404 until the flip).

**(2) Code push (branch onto `main`): Safe.** `[5/9]` "No pending migrations"; the seed creates only `since: 3` rows for roles at `defaultsVersion` 2 (create-only `update: {}`, `seed.ts:104-153`), two notification-settings rows, ten form rows; the descriptor registers unconditionally and boot conformance printed `0 undecorated` on the same compose with the flag both ways (§B); no import-time env read anywhere in `modules/website` (`website-env.spec` pins the single reader); the DI graph (`SalesModule`, `CareersPublicModule`, `UploadModule`, `NotificationsModule`) resolved in the §B boot and is one-way; both crons return at the top of the tick while the flag is `false`; a stale browser bundle only warns on the hash (`permissions.ts:156-164`).

No path crash-loops or grows unbounded.
